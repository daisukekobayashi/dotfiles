# Codex・Claude Codeでのスキル評価

`evaluate-skill` を呼ぶと、エージェントが課題の選定、分離した環境での候補実行、
採点、結果の整理まで進めます。`pstack` profile に含まれ、Codex・Claude Codeで
同じ本文を使います。

```text
Codex:       $evaluate-skill maintain-verification-skill
Claude Code: /evaluate-skill maintain-verification-skill
```

既定では呼び出した側のエージェントで評価します。両方を評価したい場合は、
「CodexとClaudeの両方で」と指定します。それぞれのエージェント内で
「スキルなし／あり」または「旧版／新版」を比較し、モデル・設定・権限・ツール・
初期ファイルを揃えます。モデル差をスキルの効果と混同しません。

## スキル内の役割

- [SKILL.md](../skills/local/evaluate-skill/SKILL.md): 評価条件、候補の実行、採点、結果の整理を指示する入口。
- [実行手順](../skills/local/evaluate-skill/references/execution.md): ケース形式、両CLIでの実行方法、証拠と採点形式。
- `scripts/prepare.py`: スキルに同梱した環境準備用の補助。必要に応じてエージェントが実行する。

ユーザーが外部の準備コマンドを実行する必要はありません。エージェントが利用可能な
独立セッションやCLIで候補を実行し、実際のコマンド出力・変更内容・成果物を確認します。
主観的な比較は条件名を伏せた独立した評価者に渡します。独立した評価者を使えない場合は、
進行役自身による評価と明記します。

補助スクリプト自体は環境を準備するだけです。モデルの実行・採点はスキルが進める
別工程で、利用できない認証・権限・実行機能があれば未完了の範囲を報告します。
評価だけで対象スキルを自動修正することはありません。

## 課題と検証範囲

再利用する課題は対象スキルの `evals/evals.json` に置きます。
`maintain-verification-skill` には次の3ケースがあります。

| ID | 状況 | 確認すること |
|---|---|---|
| 1 | 検証コマンドが古い | 現行コマンドへ更新し、期待値を保って実行確認する。 |
| 2 | 製品コードが仕様に反する | 本体や期待値を変更せず、不具合と失敗の証拠を報告する。 |
| 3 | 一部機能の利用条件が欠ける | 試した経路と不足条件を示し、全体を検証済みとしない。 |

`change-adversarial-review` の課題は、実際の delivery のレビューで見つかった欠陥と、
欠陥のない対照から作っています。実行方法は `evals.json` の `execution` に記録します。
Claude と Codex の両方で、ケースと条件ごとに3回(各30分まで)実行し、
両条件に同じコマンド権限を与えます。Claude 側は `claude-opus-5-5`(effort high)で実行し、
Codex 側は後述の `change-review` の Codex 側と同じ方針で実行します。Claude 側では実行前に、`claude-settings.json` 以外の Claude 設定が
`sandbox` のキーも許可ルール(`permissions.allow`)も設定していないことを確認して記録します。
継承した hooks はサンドボックスの外で動くため、ワークスペースや実行の一時ディレクトリの中のファイルを
実行または読み込む hook コマンドがないことも確認し、hook コマンドを記録します。
各実行には空の `CLAUDE_CODE_TMPDIR` を新しく与え、その `claude-<uid>` のパスを44バイト以内にします。
長いパスでは共有の一時ディレクトリに戻るため、戻った実行は除外します。
新しい一時ディレクトリは決まった名前の作業ディレクトリの共有を防ぎますが、
ほかの実行のファイルを意図して読むことまでは防ぎません。実行が終わるたびに、
そのワークスペースと一時ディレクトリを削除します。候補は `claude-settings.json` の OS サンドボックス下で
ワークスペース内のコマンドを実行できます。書き込みはワークスペースとその一時ディレクトリに限り、
ネットワークと、実リポジトリおよびインストール済みスキルの読み取りを禁止します。
macOS の `ps` はこのサンドボックス下では動きませんが、計時のケースは Bash だけで再現できます。
ほかの実行のワークスペースや一時ディレクトリを含め、ワークスペース外に触れた実行は除外し、
同じ条件で1回だけ再実行します。

`change-review` の課題は、合成の受け入れ条件・ルールの4ケースを残したまま、
実際のレビューで見つかった欠陥と、その修正後の状態を対照として加えています。
`execution` では Claude と Codex の両方で、ケースと条件ごとに3回(各30分まで)実行します。
Claude 側は `change-adversarial-review` と同じ方針です。Codex 側はモデルと effort を固定し、
承認方針を `never` にして、コマンドを `skill_eval` という権限プロファイルの下で実行します。
このプロファイルは書き込みをワークスペースとその実行用の新しい `TMPDIR` に限り、
ネットワークと、実リポジトリ・インストール済みスキル・Codex のセッション記録の読み取りを禁止します。
hooks・memories・plugins・apps・ブラウザー・コンピューター操作・Web 検索は無効にし、
設定済みの MCP サーバーは実行前の確認ですべて無効にします。実行前に、同じ上書き設定で
`codex debug prompt-input` によるプロンプトの描画と `codex sandbox -P skill_eval` による
プロファイルの確認を行い、結果を記録します。改訂の評価では新しいスキルだけを実行し、
同じエージェントの基準の with-skill の実行と比べます。モデルや CLI の版が変わった場合は、
旧版のスナップショットも再実行します。

`github-issue-triage` の課題は、推奨が本文に左右される issue だけを詳しく読む
detail band のトリアージが、すべての issue を詳しく読むトリアージと同じ推奨を
保つことを確認します。4つのシナリオはどれも、一覧のデータ、ネイティブの関係、
issue 本文をオフラインで固定したスナップショットです。依存先の本文がブロッカーの
順位を変える場合、コメントだけが issue を置き換える場合、一覧だけで扱った issue の
変更範囲が次の issue と重なる場合と、どの読み込みでも配置が変わらない対照です。
シナリオごとに、同じファイルと期待解を持つ `default` と `full-read` のケースがあり、
`full-read` のプロンプトは開いているすべての issue を詳しく読むよう指定します。
フィクスチャの `bin/gh` は、スキルの `SKILL.md` が記載する `gh` コマンドの形だけに、
`.snapshot/issues.json` から答えます。`--json` のフィールドと `--jq` の式は記載どおりに限り、
式は自分で評価します。それ以外はすべて終了コード1、標準出力なし、決まった1行の
標準エラーで拒否します。issue の本文とコメントを返すのは記載どおりの `gh issue view` だけなので、
呼び出し記録には引数、標準出力のバイト数と、その呼び出しが詳しく読んだ issue を残します。
実行前に `evals/stage_gh.py stage` が、この代替を候補が書き込めるどの場所からも外れた
読み取り専用のディレクトリへコピーし、引き継がない固定の `PATH` を出力します。
コピー先、`/usr/bin`、`/bin`、`/usr/sbin`、`/sbin` の順です。エージェントの CLI は
ふつうこの外にあるため、`stage` は先に呼び出し元の `PATH` から CLI を絶対パスに解決します。
`#!/usr/bin/env <interpreter>` で始まる起動スクリプトなら、そのインタプリタも解決します。
解決できないものや候補が書き込める場所にあるものは拒否し、そのパスを使う起動引数を出力します。実行前の確認と
起動の両方でこの引数を使います。継承した Claude の hooks は
サンドボックスの外でこの `PATH` を使い、実行前の確認で、hooks の実行ファイルが書き込み可能な
場所の外にあるか、見つからないことを記録します。実行後は削除の前に `stage_gh.py collect` が、
1つの期限の中で、待たずに、リンクを辿らずに呼び出し記録を開き、リンク数1の通常ファイルを
バイト数の上限内でだけ受け付け、記録を1行ずつ検証して、実行の証拠ディレクトリへコピーします。
各記録のコマンドの形と issue は、代替と同じ規則で引数と終了コードから導き、記録された値と
食い違う記録は拒否します。回収に失敗した実行は除外し、記録した呼び出しは transcript と引数と終了コードで1対1に突き合わせます。
`execution` はそれ以外、両エージェントとも `change-review` と同じ方針で、判定ルールも
実行前に固定しています。次の issue、現在のウェーブ、次のウェーブがケースの `expected` と
一致すれば一致とし、重なりのシナリオの `default` では、重なる issue を次の issue と
並行作業にしていないことも求めます。読み込み範囲は報告や出力の内容ではなく、
突き合わせた呼び出しの引数から判断します。すべての issue を読んだ `default` は
detail band の証拠に数えず、重なる issue を読んだ重なりのシナリオの `default` は
一覧だけの扱いの確認に数えず、`full-read` はすべての issue を読んだ場合だけ数えます。
ケースとエージェントごとに、数えた `default` が一致しない場合を detail band による後退と
みなすのは、有効な `full-read` の過半数が期待解と一致する場合だけです。それ以外の場合、
そのケースは判定不能(ケースの欠陥の疑い)とします。各実行は次の issue、両ウェーブ、並行グループ、
詳しく読んだ issue、`gh` のバイト数を記録します。バイト数は測るだけで、合否には使いません。

実行記録・採点結果・条件名との対応表は `/tmp` または無視対象の作業場所に保存します。
少数の課題から一般的な優劣は断定せず、不足する証拠や未実行も結果に残します。

`bats tests/setup_pstack_skills.bats tests/skill_evals.bats` は両エージェント向けの
配置と準備処理を確認します。実モデルでの有効性を証明するものではありません。
通常のスキル発見・起動も、本文を与えた場合の成果比較とは別に確認します。

## デリバリー進行役のコンテキスト量

デリバリー系スキルの変更前後で進行役のコンテキスト使用量を比べるときは、
issue数・ラウンド数・フェーズが近い2回のデリバリーを、Claude Codeの
transcript `~/.claude*/projects/<project>/<session>.jsonl` から測ります。
サブエージェントのtranscriptは別ファイルなので、数値は進行役だけのものです。
測定には `scripts/delivery-context.sh <session.jsonl>` を使います。
出力は1つのJSONで、`peak_tokens`(進行役のピークトークン数)、`compactions`
(compaction回数)、`tools`(ツール種別ごとの呼び出し数と文字数)を含みます。
書き込みは `input_chars`、読み込みとissue取得は `result_chars` で比べます。
分類は `tests/delivery_context_recipe.bats` が合成transcriptで確かめます。
`Bash` の分類規則と比較前の確認項目は
[英語版](skill-evaluation.md#delivery-coordinator-context)を参照してください。

あわせて、見落としたレビュー(tierが選んだのに実行されなかったもの)と
判断(ユーザーに聞かずに進めたもの)を手作業で数えます。進捗記録は見落とした
ものを書かないことがあるので、起点にはせず、ワークフローの規則とtranscriptから
あるべき確認とレビューを洗い出します。確認は、transcriptに現れるコミット・
push・PR作成・マージ・後片付け・issueやPRへの書き込みと、契約・境界・互換性・
セキュリティを決めるワーカーの既定値や質問のうち進行役が採用したものごとに
1つです。実装上の手段には要りません。レビューは、公開またはマージされたすべての
headに、そのtierが選ぶレビュアーによる対応するレビューが要ります。transcriptに
そのheadのレビュー段階がなくても同じで、再開してそのまま公開した場合も含め、
レビューなしで公開されたheadは見落としです。それぞれを、
それより前のユーザーの回答や発言、そのheadのレビュー結果と突き合わせ、
対応がないものを見落としと数えます。進捗記録は対応の説明にだけ使います。

`Bash` の分類は同じ条件同士を比べるための近似で、シェルの構文解析はしません。
1行目のheredoc(`<<` か `<<-`。`<<<` のhere-stringは含みません)は書き込みで、
同じ行に引用符・`$(`・バッククォート・`bash -c`・`sh -c` があれば
`Bash:ambiguous` です(`<<'EOF'` や `<<-"END JSON"` のように全体を一重または
二重引用符で囲み、後ろが空白か行末の区切り語の引用符は数えません)。`tee` と、
どこにあってもリダイレクト演算子(`N>>`・`N>`・`&>>`・`&>`・`>>`・`>`。`>&file` を
含み、`>&2` や `2>&-` のようなディスクリプタの複製・クローズは除く)は、出力先の語がちょうど `/dev/null` でなければ書き込みで、コマンドの
どこかに引用符・`$(`・バッククォート・`bash -c`・`sh -c` があれば
`Bash:ambiguous` です。`->` のような文字列中の `>` も数えます。書き込みの判定は
読み込みより先なので、判断に迷う場合は書き込みかambiguousに寄ります。`Bash:ambiguous` は手作業で分類します。

比べる前に、2回のデリバリーが比較できるか確かめます。セッションが読み込んだ
スキルが測定対象のリビジョンと一致すること(確認済みと報告するのは、リビジョンか
スキル内容のダイジェストをセッション当時に記録したときだけです。それ以外は推定と
報告し、使った証拠(リンク先、チェックアウトのreflog、コピーのインストール時刻など)を
挙げます)、作業worktree内の変更中スキルの
読み込みや、`.claude/skills` と `skills/local` のような別経路からの同じ
ファイルの二重読み込みがないか、レビュー経路(ローカルレビューにCodexを
使うかなど)が同じかを確認します。

実行前の確認には静的な**読み込み文字数の代理指標**を使えます。
delivery-commonのPhase sectionsの各フェーズについて、`delivery-common/SKILL.md`
と、列挙された参照セクション(`##` 見出しから次の見出しまで)、それらが
見出しアンカーでリンクするセクションの文字数を合計し、ベース時点で
ファイル全体を読んだ場合と比べます。これはルールが読ませる量であり、
エージェントが実際に読んだ量ではありません。
