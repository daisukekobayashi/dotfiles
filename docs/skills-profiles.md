# Skills Profile Design

This document records the planned skill management model for this dotfiles repository.

## Goals

- Keep globally visible skills small and focused.
- Use project-scoped skills for repository-specific work.
- Keep frequently used skill groups curated in dotfiles so each repository does not need to rediscover them.
- Prefer official `skills` CLI behavior for third-party skills whenever possible.
- Keep custom local skills owned by dotfiles.

## Scopes

### Project Scope

Project scope is the normal mode for repository work.

Running from any directory inside a Git repository should resolve the repository root with `git rev-parse --show-toplevel`.

Expected command shape:

```sh
~/.dotfiles/setup.sh skills --scope project --profile office
~/.dotfiles/setup.sh skills --scope project --profile base,github --agent codex
~/.dotfiles/setup.sh skills --scope project --profile base,beads
~/.dotfiles/setup.sh skills --scope project --profile base,azure-devops
~/.dotfiles/setup.sh skills --scope project --profile workbench
~/.dotfiles/setup.sh skills --scope project --profile base --copy
```

```powershell
.\setup.ps1 skills --scope project --profile base
.\setup.ps1 skills --scope project --profile base -Copy
```

Project scope requires an explicit `--profile`. If it is omitted, setup should fail rather than installing an implicit default.

Setup runs the official `skills` CLI for external skills in a private staging directory outside the project, then moves the generated `skills-lock.json` and agent skill directories into the project.

Custom local skills are not written into `skills-lock.json`. They are linked from dotfiles into each selected agent's project skill directory.

Project output:

```text
repo/
  skills-lock.json          # Generated by skills CLI for external skills
  .agents/
    skills/                 # Codex project skills
    skills-profile.json     # Dotfiles-specific profile metadata
  .claude/
    skills/                 # Claude Code project skills
```

Do not automatically edit `.gitignore`. Print a reminder that `.agents/skills/` and `.claude/skills/` are generated/link targets and can usually be ignored.

### User Scope

User scope is a special dotfiles bootstrap mode, not the default model for normal repositories.

`./setup.sh skills` should remain a user-scope command and should behave like:

```sh
./setup.sh skills --scope user --profile base --agent codex --agent claude-code
```

User scope should build one dotfiles-managed user skill view and link the user agent config directories to it:

```text
~/.dotfiles/.agents/user/skills/
~/.dotfiles/.agents/user/skills-profile.json
~/.agents/skills  -> ~/.dotfiles/.agents/user/skills/
~/.claude/skills  -> ~/.dotfiles/.agents/user/skills/
```

When user profiles are changed, rebuild this single user skill view instead of keeping separate view directories per profile combination. The selected profiles are recorded in `skills-profile.json`.

For Codex user skills, keep using `$HOME/.agents/skills` because that is the path documented by OpenAI Codex skills documentation. Do not rely on the `skills` CLI global Codex path if it differs.

User-scope regeneration preserves externally synchronized skills under `synced/`; profile-managed skills are regenerated from the selected profiles. `synced` and `anthropic-skills` are reserved names in any letter case: a profile that declares either as a local or external skill fails `profile validate` and installation in every scope with `Invalid or reserved skill name: <name>`, and an install that produces a top-level entry with either name, in any letter case, fails with `skill entry collision in user staging: <entry> (<source>, reserved name)` without replacing the user view, or with `skill entry collision in project install: <entry> (<source>, reserved name)` and restores the project.

### GitHub Workflow Composition

Issue tasks use `github-issue-create`, `github-issue-triage`,
`github-issue-review`, and `github-issue-start` as needed. The start skill
prepares an isolated worktree and continues implementation.
`github-worktree-cleanup` removes completed local worktrees and branches after
safety checks and approval, and proposes deleting the remote branch when its tip
still matches the merged PR head.

`github-pr-create` creates or reuses a PR from a published branch;
`github-pr-publish` owns verification, commit, push, and PR creation.
`github-pr-review` provides a read-only review. Request AI review with
`$github-pr-review-request #123 codex`, `copilot`, or `both`. Provider-specific
procedures live in that skill's `references/` directory.

`github-pr-publish-and-ai-review-request` composes publication and requests to
both providers. `github-pr-codex-review-cycle` publishes, requests Codex, waits
for one review, prepares fixes through `github-pr-ai-review-followup`, publishes
the verified fixes, and invokes its Writeback phase. It does not automatically
request another review after fixes. Composite skills own ordering and handoffs;
underlying skills own operation details.

`github-issue-delivery` coordinates the full issue workflow: isolated worktree,
a `shared-understanding` of each issue, `design-preflight-with-docs`,
implementation, both local reviews, the PR Codex
review cycle, confirmed merge, and confirmed local cleanup. Invoke it with issue
numbers, for example `/github-issue-delivery 12 36` in Claude Code or
`$github-issue-delivery 12 36` in Codex. Use `base,github` for its prerequisites.
Both hosts use the `change-review` and `change-adversarial-review` skills and
run each in a fresh subagent of the current host, reporting the reduced
independence. Another tool, such as Codex through the installed Codex plugin's
read-only `task` runtime on Claude Code, runs them only when the user explicitly
names it.
An explicit full delivery request selects the delegated preflight, local review,
and PR-cycle phases; automatic discovery alone does not authorize them.
Each issue's worker reads the issue and code and drafts the shared understanding
and the preflight questions with recommendations; the coordinator verifies the
drafts and asks the user one issue and one point at a time, so no subagent asks
the user. Workers default only implementation tactics, return contract,
boundary, compatibility, and security decisions as questions, and report every
default they chose. Without delegation, the coordinator drafts and asks itself.
It repeats review after worthwhile fixes within bounded rounds, preserves resume
records outside tracked docs, and requires separate target-specific merge and
cleanup confirmation. Checkpoint commits before local branch review follow the
applicable commit approval rules. The standalone PR cycle retains its one-review
behavior; the delivery skill owns repetition and final completion checks.

The local `change-review` and `change-adversarial-review` skills started as
adaptations of the OpenAI plugin's review commands and now carry local review
rules. Each definition records its upstream sources and the compared commit.
The explicit-only `change-security-review` skill shares their target selection
and finding tags and reviews a change for exploitable vulnerabilities, drawing
on OpenAI's `codex-security` diff review workflow. It reads optional
`SECURITY.md` files from the reviewed repository's base as its threat-model policy.
All three read an optional root `REVIEW.md` at the base as review policy; it can
narrow focus and skip paths for the normal and adversarial reviews, but never
skips a sensitive path or lowers material or security criteria.
Delivery workflows run it as a third local reviewer when the change's risk tier
is High or the diff touches a sensitive path. A repository can add or exclude
default sensitive paths in a `## Delivery sensitive paths` section of its root
`AGENTS.md`; this repository excludes Markdown under `skills/` except in
`delivery-common`, the `*-delivery` skills, the `change-*review` skills, and
the skills that delete local or remote resources or write to GitHub or Azure
DevOps (the worktree, runtime, and beads merge cleanup skills, the GitHub and
Azure DevOps PR skills, `azure-devops-common`, and the issue and Work Item
create and start skills).
The shared `delivery-common` risk tier (Low, Medium, High) is set from the change rather than its author, and
scales the review effort through one per-tier table: the preflight depth, the
local reviewers and round limits, the hosted review rounds, whether the merge and
cleanup confirmations are combined, and the recommended human review (AI only,
one human, or multiple humans) shown before publication and at merge
confirmation. A Low change gets a short preflight read-back, `change-review`
alone, one hosted round, and one confirmation that names the PR merge and the
exact previewed cleanup targets; Medium and High keep the two-reviewer local
review. The heaviest tier recorded in a delivery governs, so the procedure
never lightens within it. The tier is not written into PR bodies, and explicit
merge, push, and cleanup approval is required at every tier. Matt Pocock's `code-review` remains available
for separate Standards/Spec reviews; it is not the delivery default.

Do not add a separate external skill pool/catalog file. Profiles are the source of truth for curated external skill groups.

The root `skills-lock.json` should stop acting as a global all-skills catalog after this migration. If the dotfiles repository itself needs project-scoped skills, root `skills-lock.json` can be generated for this repository like any other project.

### Delivery Policy Layering

Delivery skills are layered into a shared policy layer and thin provider
adapters.

- `delivery-common` is the home for delivery policy shared by both providers:
  what happens, when, and at what depth. This covers the risk tier, review
  selection, completion and merge gates, and human review recommendations and
  the points where approval is required.
- Provider delivery skills (`github-issue-delivery` and
  `azure-devops-work-item-delivery`) own how each phase is performed on their
  provider: PR creation and publication, API and CLI calls, hosted review
  cycles, and provider-specific state such as Work Item links and state
  transitions. They reference `delivery-common` for shared policy instead of
  restating it, and forward approvals to the component skills they call, such
  as `github-pr-publish`, which keep their own approval rules.
  Per-tier review effort, including the hosted review round limits, is shared
  policy in the Risk Tier's table. How a hosted review runs and when its delta
  needs another round, such as the Codex trigger and the material-delta test,
  stay in the provider's skill.

`delivery-common` holds the Worker Dialogue (worker dispatch through the start
skill, workers draft the shared understanding and design preflight, the
coordinator asks the user, and the preflight and implementation handoff), the
Local Review procedure (snapshot pinning, finding assessment including
follow-up candidate recording, focused follow-up, reviewer selection, and local
review escalation, advancement criteria, round counting and limits, and the
head and coverage record), the Risk Tier, and Delivery Completion (the progress
record, resume, the decision summary shown before publication and at merge, the
published-head check and advance after publication, merge confirmation contents, delivery
bounds and stop conditions, the final report and `Complete` rule, and
end-of-delivery follow-up candidate reporting and creation). Its `SKILL.md` says
the calling workflow owns how its hosted review runs and approvals. Its
Delegated Authorization section states once how a caller passes the user's
request, exact target, and existing approvals to the skills it calls; the PR,
review request, and delivery skills of both providers link it, and each keeps
its own approval model. Its Missing Prerequisites section states once that a
missing skill, reviewer, or tool stops the phase that needs it for the affected
targets and is reported as a blocker, never installed, substituted, or skipped;
both provider delivery skills and Local Review link it. The shared text is
provider-neutral: it names the task and task closure, and marks where the
calling workflow adds its own items. Each provider skill lists only those
additions next to its link, such as the hosted review outcome on GitHub or the
proposed Work Item state transitions on Azure DevOps.

Shared delivery policy lives in `delivery-common`; restating it in a provider
delivery skill is drift. A policy change that applies to both providers edits
`delivery-common` once and updates the ownership statement and the frontmatter
`description` in `delivery-common/SKILL.md` to match. Provider-only policy stays
in the provider skill. Both provider skills deliberately keep one short
restatement as a local guard that tests pin: the one-line run of the shared safe
branch name check (see [Shared Scripts](#shared-scripts)) in their resume
paragraph, before any command uses the recorded branch. The rest of resume
lives in Delivery Completion, and the shared understanding status gate lives
only in the Worker Dialogue.

Azure DevOps parity is the default. Policy in `delivery-common` applies to both
providers automatically. When a change on one provider also requires
provider-specific changes to the other provider's skills, make them in the same
issue and PR. Defer the Azure DevOps side only when it needs Azure-specific
investigation, such as Azure DevOps APIs or policies, and only with a tracked
follow-up issue. Intentional provider differences are not drift. They are:

- Azure DevOps omits the hosted AI review cycle, so its delivery has no hosted
  review round limit, hosted re-review condition, or return from hosted fixes
  to local review.

Both provider delivery skills link the same `delivery-common` files;
`setup/test/skills-wiring-delivery.test.mjs` fails when one provider adds or
drops such a link.

### Shared Scripts

Checks that several workflow skills repeat live once as scripts in
`skills/local/delivery-common/scripts/`, and each calling step states the rule
in one line that runs the script. This location is in `base` and also serves
skills outside delivery, such as the PR, cleanup, and Beads skills, so every
profile whose skills call a script needs `base`: use `base,github`,
`base,azure-devops`, or `base,beads`.

- Scripts are Node `.mjs` files, so they run on macOS, Linux, and Windows,
  where setup already requires `node`.
- A calling skill links the script relative to its own directory
  (`../delivery-common/scripts/<name>.mjs`), which resolves in linked and
  copied installs because skills are installed side by side.
- A missing script, a missing `node`, or any unexpected exit stops the calling
  step; it never falls back to an unchecked path.

`check-branch-name.mjs` defines a **safe branch name**: non-empty, only
`[A-Za-z0-9/._-]`, and not starting with `-`. A caller runs
`node <script> -- '<name>' ...` with each name single-quoted, and writes a name
into this or any command only when it uses solely ASCII letters, digits, `/`,
`.`, `_`, and `-`; any other name is unsafe without running anything, because
some shells treat more than `'` as a quote, such as PowerShell with
U+2018-U+201B. The script stays the authority for the leading `-` and any later
rule. Exit 0 means every name is safe, 2 is a usage error, and 3 means at least
one is unsafe (each reported on stderr); any other status, including the 1 that
`node` returns for a missing script, means the check could not run. A host
shell may report a non-zero status other than 3, as PowerShell reports 1, so a
caller that branches on unsafe also accepts a non-zero exit whose stderr is one
or more `unsafe branch name:` lines and nothing else. The start, delivery, PR,
Codex review cycle, and cleanup skills of both providers and the Beads worktree
and merge cleanup skills check their branch; the PR create and publish skills
also check their base or target branch. `azure-devops-work-item-start` skips
comparing an open PR only for a name outside that ASCII set, exit 3, or a
non-zero exit whose stderr is one or more `unsafe branch name:` lines and
nothing else, and stops on any other failure. Worktree paths, bead ids, the
head owner (which `github-pr-create` checks with its own rule), and base
branches outside the PR create and publish skills are not checked by it.
`tests/check_branch_name.bats` covers the script.

`check-push-target.mjs` enforces the **push target rule**: push only to the
remote the user named, or the single remote that names the repository, with an
explicit `<branch>:refs/heads/<branch>` refspec; with more than one remote and
none named, ask, even when exactly one of them names the repository. In a fork
layout `gh repo view` can resolve the parent, so the one matching remote may be
the parent; asking covers every fork layout without per-remote API lookups, and
`github-pr-create` still verifies the created PR's head repository. The caller
passes the repository it resolved (`--github <host> <owner>/<repo>` or
`--azure <org> <project> <repo>`), and the script reads only local git
configuration and remote URLs, with no `gh`, `az`, or network call. `resolve`
prints the remote on line 1 and, for GitHub, the head `<owner>/<repo>` on
line 2; Azure DevOps URLs must use one of the accepted remote URL shapes in
`azure-devops-common/references/context.md`. A named GitHub remote may name
any one `<owner>/<repo>` on the host, which becomes the head repository; a
named Azure DevOps remote must name the given repository in its fetch and every
push URL. `pre` and `post` check the
branch's upstream before and after the push, which stays a visible
`git push -u <remote> <branch>:refs/heads/<branch>` command in the skill so
approval and permission rules still see it. Exit 0 means the check passed, 2 is
a usage error, and 3 means the check failed: the caller asks the user to name the
remote after `resolve`, and stops and reports after `pre` or `post`. Any other
status means the check could not run and stops the push. The GitHub and Azure
DevOps publish skills, `github-pr-create` on direct invocation, and
`github-pr-codex-review-cycle` on a resume without the captured remote run it.
`tests/check_push_target.bats` covers the script.

`check-cleanup-targets.mjs` holds the **remote branch deletion check** and the
**cleanup target manifest** for `github-worktree-cleanup` and
`azure-devops-worktree-cleanup`. `remote` proposes deleting the remote branch
only when the PR's head repository is not a fork, the push target rule resolves
its remote and that remote names the PR head repository,
the PR is merged (completed on Azure DevOps), the branch is not the default
branch, protected, or under policy, no other open PR uses it, and
`git ls-remote` returns exactly the PR head, and then prints the SHA to lease
against; otherwise it keeps the remote branch. The cleanup target manifest records the worktree, local branch, that
remote branch result, the processes and Compose projects with their volumes that
`worktree-runtime-cleanup`'s read-only listings report, and the run-owned
temporary paths the caller passes. It also records the PR head repository. `manifest` writes it as JSON to a new
file outside the worktree, created with mode 0600, and prints the targets for confirmation; with `--preview` it is the
Caller preview for a combined merge and cleanup confirmation, made before the
merge. `compare` builds it again right before any removal and fails on any
difference from the confirmed manifest, except a confirmed remote branch that no
longer exists, such as one the host deleted on merge. A listing that cannot run or reports an error on stderr
fails a Caller preview and its compare; otherwise it is reported as unverified
and must be unverified at confirmation as well. The caller looks up the provider
facts with `gh` or `az` and passes them in, stopping the cleanup when a lookup
fails; the script reads only git, process, and Docker state, runs `git ls-remote`
itself, and never deletes, stops, or signals anything. Exit 0 means the check
passed, 2 is a usage error, and 3 means the check failed: `remote` keeps the
remote branch and cleanup continues without it, while `manifest --preview` and
`compare` stop the cleanup. Any other status means the check could not run and
stops the cleanup. `tests/check_cleanup_targets.bats` covers the script.

## Profile Format

Profiles are JSON so setup can process them with Node without adding a parser dependency.

Example:

```json
{
  "description": "Office document skills",
  "external": [
    {
      "source": "anthropics/skills",
      "skills": ["docx", "pdf", "pptx", "xlsx"]
    }
  ],
  "local": []
}
```

Rules:

- `includes` contains other profile names.
- `external[].source` is an `owner/repo` source passed to `npx skills add`.
- `external[].skills` contains skill names from that source.
- `local[]` contains names under `skills/local/`.
- Includes are expanded as a union.
- Duplicate skills are ignored.
- Cyclic includes are errors.
- Missing profiles, missing local skills, and malformed external entries are errors.
- Domain profiles should generally stay independent. Compose `base` explicitly, or use a dedicated aggregate profile such as `workbench`.

## Initial Profiles

### `base`

Provider-neutral workflow skills used broadly across repositories.

Include:

- `frontend-design` and `webapp-testing` for UI creation and testing
- `playwright-cli` for browser automation and `context7-cli` for library documentation lookup
- selected published Matt Pocock Engineering and Productivity skills
- `repo-execution-context`, `change-review`, `change-adversarial-review`, `change-security-review`, and runtime isolation local skills
- `delivery-common` for the shared worker dialogue, committed-snapshot local review procedure, risk tier, and delivery completion policy
- `shared-understanding`, which before design preflight reads an issue or Work Item back to the user with a before/after example and settles with them what it decides and what it leaves undecided
- `git-commit`

Matt Pocock `misc`, `personal`, `in-progress`, and `deprecated` skills are not included.
Superpowers is not included in `base`. Use `writing-for-agents`, the upstream replacement for `writing-great-skills`.

Use `base,github` when you want the previous GitHub-enabled baseline.

### `pstack`

Eleven local adaptations of Lauren Tan's pstack. This profile is independent of
`base` and `github`; it adds no external packages, plugin hooks, model settings,
or default routing. Existing `tdd` and `teach` skills keep their names and owners.

| Skill | Responsibility |
|---|---|
| `how` | Read-only explanation of current execution, data flow, and ownership. |
| `why` | Read-only design history from Git, PRs, issues, and ADRs, separating evidence from inference. |
| `architect` | Caller usage and contract design; implementation follows the original request's authorization. |
| `arena` | Independent candidate comparison with shared criteria, isolated writers, and verified synthesis. |
| `interrogate` | Read-only independent reviews and evidence-based synthesis. |
| `blast-radius` | Explicitly requested impact verification using isolated probes, without repairing the implementation. |
| `create-verification-skill` | Generate and exercise project-local verification procedures and a feature map. |
| `maintain-verification-skill` | Reconcile an existing verification skill with source and live behavior, preserving product contracts. |
| `evaluate-skill` | Coordinate isolated skill comparisons, blinded grading, and evidence-based recommendations on either agent. |
| `prove-it-works` | Shared principle for matching completion claims to observed behavior. |
| `encode-lessons-in-structure` | Shared principle for preventing evidenced recurring failures with focused safeguards. |

Example invocations: `$how trace this request`, `$why was this state persisted?`,
`$architect design this interface`, `$arena compare these approaches`,
`$interrogate review this change`, `$blast-radius check this schema change`,
`$create-verification-skill for this CLI`,
`$maintain-verification-skill for this app`, and
`$evaluate-skill maintain-verification-skill`. Claude Code exposes installed skills
through its own invocation interface. The two principles can be consulted
directly or by the workflow skills.

`arena`, `interrogate`, `blast-radius`, `create-verification-skill`,
`maintain-verification-skill`, and `evaluate-skill` require explicit user invocation. Their descriptions
and instructions enforce this
boundary, with `policy.allow_implicit_invocation: false` for Codex and
`disable-model-invocation: true` in SKILL.md frontmatter for Claude Code.
Use `$skill-name` in Codex or `/skill-name` in Claude Code. References from
another skill do not activate these workflows; `architect` compares alternatives
directly unless the user explicitly invokes `arena`.

`how`, `why`, and `architect` remain discoverable by their task descriptions.
The two principles can be consulted when relevant or by another workflow.
Availability does not mean every task runs all eleven workflows. Parallel
candidates/reviewers are bounded and conditional; unavailable delegation is
reported as a limitation, not simulated independence.

`architect` consults `codebase-design` when available and leaves explicitly
requested preflight to `design-preflight`. `interrogate` reads criteria from
`change-review` and `change-adversarial-review` when available without invoking those
explicit-only workflows. Standalone `pstack` provides small fallback criteria.
Read-only investigation/review stays separate from executable probes and fixes.
Commit, push, dependency, remote-write, and destructive-operation approvals
remain governed by the user's instructions.

Install after the sources are in the checkout that should own the live links:

```sh
./setup.sh skills profile validate --profile base,github,pstack
SETUP_DRY_RUN=1 ./setup.sh skills --scope user --profile base,github,pstack
./setup.sh skills --scope user --profile base,github,pstack
```

User scope rebuilds one shared view; include every profile you want to retain.
The `pstack` profile itself is local-only, but the combined `base` profile may
run the external skills CLI. Review that plan and required execution approvals.
Avoid installing live user links from a temporary worktree that will be removed.
For a project, use `--scope project --profile base,pstack` instead.

The reusable generator belongs in user scope. Generated verification commands,
feature maps, and reusable helpers belong in the target project's established
skill directory. Each generated procedure is a draft until exercised, and its
reported coverage is limited to the paths actually run. Run-specific evidence
belongs in ignored temporary storage and survives process cleanup.

`maintain-verification-skill` uses one instruction body on Codex and Claude Code.
It reports incomplete coverage as blocked and keeps product repairs outside its
scope. The explicit [evaluate-skill workflow](skill-evaluation.md) owns candidate
execution, grading, and synthesis, with its preparation helper bundled inside
the skill. It uses independent fixtures and common criteria for both agents. Preparing fixtures or
validating metadata does not establish that either model followed the workflow.

The original nine adaptations use upstream revision
[`12d587dfb20741cafc376c42c696c5f6e2a64487`](https://github.com/cursor/plugins/tree/12d587dfb20741cafc376c42c696c5f6e2a64487/pstack).
Each skill includes its source link, local adaptation rationale, and Lauren Tan's
MIT license. The upstream `principle-prove-it-works` and
`principle-encode-lessons-in-structure` names are shortened locally.
The maintenance and evaluation skills record their source revisions in their
entrypoints. `evaluate-skill` adapts the upstream Eval playbook as a standalone
local skill; that name is not an upstream standalone skill.
These are curated adaptations, not an automatically synchronized plugin fork.
Compare relevant upstream changes against these local contracts before updating.

## CLI Behavior

Use TypeScript as the source of truth for profile-based skills setup. Commit the generated Node runtime so bootstrap does not require a TypeScript runtime.

Runtime entry point:

```text
setup/skills.js
```

TypeScript source:

```text
setup/src/skills.ts
```

Bash and PowerShell responsibilities:

- Resolve setup paths and environment.
- Invoke `node setup/skills.js`.

Node runtime responsibilities:

- Parse skills flags.
- Load and validate profile JSON.
- Expand `includes`.
- Merge external skills by source.
- Validate local skill names.
- Reject skill name collisions between local and external skills or across external sources.
- Call `npx skills add` for external skills.
- Link local skills.
- Back up and roll back project outputs.
- Write `.agents/skills-profile.json`.
- Wire final user-scope links.

Profile add/remove helper commands are intentionally out of scope for the first implementation. Edit profile JSON by hand and use `./setup.sh skills profile validate`.

## External Skills

For project scope, use official CLI installation:

```sh
npx skills add <owner/repo> \
  --skill <name> \
  --agent codex \
  --agent claude-code \
  --copy \
  --yes
```

Setup runs this in a private staging directory outside the project, then moves the generated `skills-lock.json` and agent skill directories into the project.

If an existing `skills-lock.json` or agent skill directory will be replaced, create a backup first and restore it if installation fails. On successful installs, copy back pre-existing agent skill entries that were not recreated by the selected profile. Entries with the same name as profile-managed skills are replaced by the profile-managed version, even when they are copies with local edits; the previous entry stays only in the backup, and setup names the backed-up entry in a `Replaced locally edited skill copy` warning when it was an edited copy. Links into `skills/local` for skills that are no longer selected or no longer exist, and unchanged managed copies of them, are not copied back; they stay only in the backup. Edited copies of those skills are kept with a warning. Pre-existing entries with a reserved name are copied back like any other entry; only entries an install produces fail on a reserved name. Dirty Git state should produce a warning, not block execution.

Setup runs each `npx skills add` in a new private directory, not in the project or a shared temp directory such as `/tmp`, for both scopes. The npm cache and project backups live in the same per-user location: `$XDG_CACHE_HOME` or `~/.cache` on Linux, `$TMPDIR` on macOS, and `%TEMP%` on Windows. The cache is `dotfiles-skills-npm-cache/` and is reused across runs; backups go to `dotfiles-skills-backup/<project directory name>/` and are kept after a successful install. `$TMPDIR` and `%TEMP%` must be absolute, and `%TEMP%` must be on a local drive (`C:\...` or `\\?\C:\...`), not a network share (`\\server\share`, or a drive letter mapped to one), a device path, or a path without a drive (`\Temp`). Setup checks these directories before creating any of them, so a refusal leaves no new directory behind. Setup stops before changing anything when one of these values is unsuitable; when that location is inside the project, regardless of letter case on Windows and on case-insensitive macOS volumes; when that location, or a directory above it, is owned by another user or writable by others; when such a directory is group-writable and is not your own directory with your user-private group (your primary group, named after you, with no other members in `/etc/passwd` and `/etc/group`), which on macOS refuses every group-writable directory; or when `.agents`, `.claude`, an agent skill directory, `skills-lock.json`, or `.agents/skills-profile.json` in the project is a symbolic link, wherever it points and even when it is dangling.

After each external install, setup checks that every requested skill has a `SKILL.md`. Missing skills prevent the user view from being replaced and trigger backup restoration in project scope. `profile validate` checks configuration structure, not upstream availability or runtime behavior.

In user scope, setup copies every entry each install produces, including entries that were not requested, into one staged view. When two installs produce an entry with the same name, setup fails with `skill entry collision in user staging: <entry> (<earlier source>, <later source>)` and does not replace the user view. When an install leaves `.agents/skills` or `.agents` in its staging directory as a symbolic link, or as anything other than a directory, setup fails with `skill entry collision in user staging: <path> (<source>, symbolic link)` or `skill entry collision in user staging: <path> (<source>, not a directory)`, copies nothing from it, and does not replace the user view.

In project scope, the installs run in sequence in one private directory. When an install removes, replaces, or changes anything inside an entry that an earlier install produced, such as rewriting a file in place, adding a file, or changing a file's permissions, even when the content stays the same, setup fails with `skill entry collision in project install: <entry> (<earlier source>, <later source>)` and restores the project from the backup. When an install leaves `.agents/skills`, `.claude/skills`, `.agents`, or `.claude` in that directory as a symbolic link, or as anything other than a directory, setup fails with `skill entry collision in project install: <path> (<source>, symbolic link)` or `skill entry collision in project install: <path> (<source>, not a directory)` and restores the project from the backup.

## Local Skills

Local skills live under `skills/local/<name>` and are dotfiles-owned.

Project scope should symlink local skills into selected agent project skill directories:

```text
repo/.agents/skills/<name> -> ~/.dotfiles/skills/local/<name>
repo/.claude/skills/<name> -> ~/.dotfiles/skills/local/<name>
```

User scope should also symlink local skills into the generated user profile view.

On Windows, when Node cannot create the project links because symbolic link privileges are missing, setup requests UAC elevation once for the whole link batch. Cancelling or being unable to elevate (Win32 code 5, 740, 1223, or 1314), or missing link privileges after elevation, falls back to copies; any other elevation failure stops setup and restores the project from the backup.

`--copy` (`-Copy` in `.\setup.ps1`) installs project local skills as copies from the start, without attempting links or elevation, on every platform. It is accepted only with `--scope project`; user scope fails with `--copy is supported only for project scope`, and `.\setup.ps1 skills -Copy` copies user-scope links in PowerShell instead. Each run follows its own flag: a run with `--copy` replaces existing project links with copies, and a later run without it creates links again.

Each copy is a plain directory with a `.dotfiles-copy-<name>.json` marker next to it, recording its source and content. Copies do not follow source edits; rerun setup to refresh them. Like every selected entry, a copy is replaced on each run, and local edits survive only in the backup.

If a target path already exists and is not a dotfiles-managed symlink, fail instead of overwriting it. Local skills take no precedence over external installs: when an install produces an entry with a local skill's name, setup fails with `skill entry collision in user staging: <entry> (<source>, local)` or `skill entry collision in project install: <entry> (<source>, local)`, keeps the user view, and restores the project.

Skill names must be unique across the selected profiles. A local skill must not share a name with an external skill, and two external sources must not provide the same name; `profile validate` and installation fail on a collision before any external install. Avoid generic names that hosts or popular skill sets already use, such as `review` or `code-review`.

## Agents

Keep profile selection separate from agent selection.

Default agents:

```text
codex
claude-code
```

Examples:

```sh
~/.dotfiles/setup.sh skills --scope project --profile office
~/.dotfiles/setup.sh skills --scope project --profile office --agent codex
```

## Metadata

Write dotfiles-specific project metadata to:

```text
repo/.agents/skills-profile.json
```

This metadata should record:

- requested profiles
- expanded profiles
- selected agents
- external install plan
- local skill links
- generator name/version if useful

Do not put dotfiles-specific metadata into `skills-lock.json`.
